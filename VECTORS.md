# Golden vectors

`tests/golden/` holds test vectors generated by the **Go** implementation, the normative reference for this
port. The generator is `tools/vectorgen`, a Go module that requires `github.com/amber-store/dstore` v0.1.9,
`github.com/amber-store/core` v0.0.8, go-udiff v0.4.1, fxamacker/cbor v2.9.3, go-iroh v0.2.0 and zeebo/blake3
v0.2.4, built with go1.26.5 (`GOTOOLCHAIN=local`, `CGO_ENABLED=0`). The Rust tests read the vectors through
`dstore_testkit::golden` (PORTING.md §7).

**Status: conventions only.** Each family's schema is added when the family lands. Families document
themselves in `tools/vectorgen/docs/<owner>.md`, and those files are assembled here.

## Regenerating

```sh
nix develop -c go -C tools/vectorgen run . ../../tests/golden              # every family
nix develop -c go -C tools/vectorgen run . ../../tests/golden FAMILY...    # only these families
```

`vectorgen <out-dir> [family...]` regenerates the named families, or every registered family when none is
named. Two runs produce identical bytes. CI regenerates twice, diffs the two runs, and diffs the result
against the committed vectors.

Two other outputs come from helper programs:

- The CLI snapshots, `tests/golden/cli/snapshots.json`, come from `go run ./cmd/clisnap`. It builds the Go
  CLI into a temporary `GOBIN` and deletes it afterwards.
- `crates/gocompat/src/tables.rs` comes from `go run ./cmd/gotables`.

## Conventions

- **JSON** is built from structs and ordered slices only, never Go maps. It is written with
  `json.MarshalIndent` (two spaces) plus a trailing newline, through `writeJSON` in
  `tools/vectorgen/util.go`. Go's HTML escaping (`<`, `>`, `&`) stays; JSON readers accept it.
- **64-bit integers** (`uint64`, `int64`, nanosecond durations and times) are decimal strings, through
  `util.go` `U64` and `I64`, because they exceed 2^53. Booleans and small integers (lengths, counts, indexes,
  `uint8` to `uint32`) are JSON booleans and numbers. Rust reads the strings with
  `dstore_testkit::golden::decimal_u64` / `decimal_i64`.
- **Bytes** are lowercase hex strings, through `util.go` `Hex`. Where nil and empty differ (`[]byte` fields
  without omitempty), nil is `null` and empty is `""`.
- **Texts** that Go produces (error messages, stdout, help) are JSON strings holding the exact bytes. A text
  that is not valid UTF-8 goes into a hex field whose name ends in `_hex` (for example `in_hex`).
- **Payloads** are described rather than inlined when they are large:
  - `{"hex": "<lowercase hex>"}`: the bytes verbatim (`util.go` `Inline`);
  - `{"seed": "<decimal u64>", "len": N}`: `data(seed, N)` of the splitmix64 stream below (`util.go` `SM`).

  Rust: `dstore_testkit::golden::Payload::bytes()`, which accepts the seed as a string or a number.
- **Node ids** are ed25519 public keys from `crypto/ed25519.NewKeyFromSeed(data(seed, 32))`, so they are
  valid points and deterministic.
- **Map order.** Where Go iterates a map (PORTING.md DD-10), vectors avoid the order or sort it. Tests never
  assert an order that Go randomises.
- **`package main` code.** Functions of `cmd/dstore` cannot be imported, so vectorgen holds verbatim copies
  of the ones it needs. Before generating, a self-check prints the module's `cmd/dstore` functions with
  `go/printer` and compares them with the copies.
- **Missing files fail.** `dstore_testkit::golden::load_json` panics when a file is missing. The vectors are
  committed, so a missing file is a test failure, never a skip.

### Deterministic data streams

Pseudo-random payloads come from **splitmix64**, exactly as in core-rs `VECTORS.md`:

```
next(state): state += 0x9E3779B97F4A7C15
             z = state
             z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9
             z = (z ^ (z >> 27)) * 0x94D049BB133111EB
             return z ^ (z >> 31)
```

`data(seed, n)`: set `state = seed`, append `next(state)` as **8 little-endian bytes** until there are at
least `n` bytes, then truncate to `n` bytes.

`u64s(seed, n)`: the first `n` outputs of `next`, starting from `state = seed`.

Rust: `dstore_testkit::splitmix::{SplitMix64, data, u64s}`. Go: `smData` and `u64s` in `tools/vectorgen/util.go`.

## Where tests live

- Vectors of crate-private functions (`batches`, `rank_owners`, `est_size`, `gosort`) are read by crate unit
  tests.
- Public APIs are tested in the root `tests/golden.rs`, one module per owner group of PORTING.md §6
  (`tests/golden_tests/<group>.rs`), so owners working in parallel never edit the same file. Each module's doc
  comment names the vector files it reads; several modules may read one file (`text/formats.json`,
  `errors/text.json`).
- The CLI snapshots run in `tests/cli_snapshots.rs`, with a clean environment (`PATH`, a temporary `HOME`,
  `TZ=UTC`) and `{CWD}` normalised through `pwd -P`.

## The generator

`tools/vectorgen/main.go` holds a registry. Each family registers itself from its own file with
`register(name, owns, gen)` in an `init` function. `owns` lists the paths under `tests/golden/` the family
owns, as clean relative slash paths of files or directories (for example `"wire/frames.json"` or
`"worktree/trees"`). `gen(out)` writes the family's files under `out`, a fresh empty directory laid out like
`tests/golden/` (for example `out/wire/frames.json`).

Registration refuses owned paths that overlap another family's, and paths that cover `cli/snapshots.json`
(written by `cmd/clisnap`) or `.gitkeep`. The command runs the selected families, each into a temporary
directory, and checks that the family produced at least one file under every path it owns and nothing
outside them. Then it deletes exactly the paths the family owns from `<out-dir>`, so stale files go too, and
copies the new files in. Nothing else in `<out-dir>` is touched. When a generator or the check fails,
`<out-dir>` is left as it was. `go test ./...` in `tools/vectorgen` covers these rules.
